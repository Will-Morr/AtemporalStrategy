# Lobbies and basic opponents

Requirements: [user specification](../user_spec/lobbies_and_bots.md).

## Current implementation

The public server runs as a coordinator. Each game has a stable `/games/<id>/` address, an isolated worker process and its own archive directory. The coordinator forwards WebSocket messages to loopback workers; simulation and match state remain in the worker. Workers begin at lobby creation to reuse the existing live roster and five-map picker, but simulation begins only after Start. This lifecycle is an implementation choice.

Coordinator metadata and per-game setup persist on disk. Workers resume from their most recent archive after a coordinator restart. Standalone worker mode remains available for native peripherals and existing tooling. Passwords are a casual per-game cookie gate, not authentication or encryption. Static assets remain on the public origin; each game pins its content and serves a matching guide beneath its game URL. Open/active workers restart automatically with the coordinator. Replay workers stop when their last viewer disconnects.

The directory remembers an unvalidated username using a browser cookie identity and records successful slot claims per game. Duplicate or empty names are allowed; this is not authentication. Game lobbies inherit the directory username without asking for it again. Clicking an open slot bar claims it, and the release button sits on the player’s claimed bar. The directory lists open, active and completed games. Creation presents common settings first and an advanced setup editor for the full existing configuration. New arrivals are spectators until claiming a slot; session tokens are scoped by game URL so switching between matches in one tab cannot erase another identity. Previous archived matches remain selectable as read-only replay workers.

Bots use published checkpoint states, filtered to player-visible enemies, and submit ordinary drafts through the controller's precheck, local-reference resolution and exact-state validation. They never inspect pending opponent commits or modify simulation state, resources or units. Human/bot games wait for human commitments; bot-only playtests start automatically and have a configurable round budget.

There are two heuristic policies. Raider grows a smaller initial economy and favors earlier, smaller attacks with grunt/grinder-heavy mixed batches and split exploration groups. Builder grows more miners, places more turrets and waits for larger forces, with tank/artillery-heavy batches. Both can produce miners, constructors, scouts, grunts, grinders, tanks and artillery, and place factories and turrets. Walls and silos are deliberately omitted. Public terrain produces repeatable map/slot-dependent opening variety, including occasional aggressive Builder openings; nondeterminism is allowed by the requirements but not needed here. Saved `rusher` configurations deserialize as Raider for compatibility.

Production counts existing and queued workers across factories, replenishes finite mixed batches, and replaces missing workers ahead of combat units. Idle constructors mine; construction takes priority while projects are active. Expansion targets grow with miner counts, up to six factories, with a current desired mining workforce of roughly 14–17. These tuning values are implementation choices. Placement uses reachable open areas and reserves existing factory outputs; turrets tend toward the current enemy or exploration direction.

Exploration remembers observed terrain and last-seen enemy structures from the current published revision up to the intervention tick. Observing an empty structure tile clears that target. Scouts traverse reachable rooms, while armies attack visible threats, remembered structures or unexplored space. Strength estimates control regrouping and attacks; badly damaged units can fall back when outmatched. This is a coarse policy, not tactical search or guaranteed effective micro.

Interventions usually advance 70 ticks (Raider) or 90 ticks (Builder), with a nearby army checkpoint preferred. Every third planning round can revisit before a large loss of own assets. Reissued unit orders replace that unit's later orders through ordinary future-order locks. Knowledge is rebuilt for the current revision, so abandoned timeline observations do not leak into a rewritten one. Single-order games rank independent actions with periodic opportunities for combat and scouting rather than truncating dependent opening plans. Validation retains other legal actions if an independent action fails; failure feedback does not reveal hidden blockers or trigger hidden-state replanning.

Verification covers coordinator process isolation, passwords, multiple games and identity retention, restart, replay browsing, bot fairness/legality, and real-browser input scenarios with inspected screenshots. See the [verification record](integration-verification.md#game-coordinator-users-and-basic-bots--2026-10-24) for results and limits.

## Simple win

The game-type selector includes `simple_win`. It uses configurable scoreboard rules (five timeline wins by default), with no advancing history. Only completed structures count as buildings, including silos; construction ability is irrelevant. The first tick ending with any player lacking buildings ends the simulation, including in teams/FFA. Same-tick losses are resolved together. This cutoff overrides `stop_when_decided`, queued orders, missiles and minimum horizons. These multiplayer and completed-building details are implementation interpretations. Other game types retain their existing survival and cutoff rules.
