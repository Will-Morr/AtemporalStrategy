# Architecture and deterministic simulation

> Status: a revisable assistant proposal unless explicitly attributed to the user. See [user specifications](../user_spec/README.md). Imperative wording describes the current candidate design, not a locked requirement.

## Processes and modules

The slice implements this architecture end to end; see [contracts v2](contracts-v2.md), [development](development.md) and [Gate 2 measurements](gate2-measurements.md). Two measured deviations from the text below: intent computation currently runs serially (parallel intents are simulation breadth work), and movement `Move` events are not emitted because 5-tick samples suffice for playback and per-step events would dominate export volume. Everything else below remains the plan breadth agents extend.

Use one Rust workspace with `content`, `contracts`, `sim`, `server`, and `runner` crates, plus a small TypeScript browser client. Server serves static game and player-guide files, HTTP bootstrap/archive endpoints and a WebSocket for live state. It owns slots, planning phases, accepted commands, scores, timing, and durable match revisions. No database; one match per server process is sufficient.

The server runs simulation work on a dedicated thread, using owned `SimRequest` jobs and typed `WorkerMessage` channels. IO never runs ticks on its event loop. A failed/canceled job leaves the last published revision intact; a cancellation flag is checked at each tick and stale job/revision results are ignored. Recoverable thread panics/errors become failed jobs with fresh per-job state; process-fatal failures still require archive recovery. The `runner` binary provides only the native peripheral, which invokes the same simulation library locally. No subprocess startup or simulation IPC is involved.

Use a bounded pool inside the simulation for expensive read-only intent calculations. Small simulations use a serial threshold to avoid parallel overhead. Use native Rust `f64`, finite values only, no fast-math and no unordered reductions. Guarantee repeatability for the same pinned build/platform; arbitrary cross-CPU or native/browser float identity is not assumed. Peripheral handshake rejects incompatible fingerprints. Forbid `HashMap`/`HashSet` in `crates/sim` with Clippy disallowed-types checks; use tile arrays, sorted Vecs or BTreeMap/BTreeSet. Browser clients do not independently simulate.

## Tick meaning and checkpoints

`S[t]` is state immediately **before** tick `t`. Commands stamped `t` are applied before that tick's actions. Running tick `t` yields `S[t+1]`. Initial state is `S[0]`; `max_tick` is exclusive. Timeline display distinguishes selected pre-tick state from events occurring during that tick.

Store periodic complete checkpoints (initial proposal every 100 ticks), sampled browser snapshots (every 5 ticks), and tick-indexed events/statistics. Players can seek/play and issue orders at any editable timeline tick, never only sampled/checkpoint ticks. Reconstruct exact S[t] in-process from the nearest earlier checkpoint (at most 99 replayed ticks at the proposed interval when that checkpoint is retained). Keep a small exact-state LRU keyed by revision/tick; regenerate evicted checkpoints if necessary. Interpolated samples can appear immediately, but staging/validation waits for exact state. The simulation adapter gives short exact-state jobs priority at tick boundaries so inspecting a published revision need not wait for a full new round to finish. Cold/rebuilt-cache latency is measured, not assumed.

To revise at `e`, load latest checkpoint `c <= e`, keep commands before `e` unchanged, execute `[c,e)` to reconstruct `S[e]`, then regenerate the suffix. Checkpoint spacing means some unchanged work is replayed; no changed tick is skipped. Reuse immutable prefix data and discard stale suffix snapshots, statistics, derived outcomes, and caches. Retain scheduled orders and player entities through temporary elimination. Effective future inputs still participate in inactivity lookahead; survivor count cannot truncate the run.

Checkpoints include every future-affecting value: tick, terrain/ore, bank, entities, order state, last successful movement direction, entity/group order locks, cooldowns, queues and active progress, sites/blueprints, control-group membership/latest orders/factory bindings, current survival status and recovery transitions, last-progress tick/inactivity state, deterministic spawn identity data, and any RNG state. Flow fields and their cache version are derived and reset on checkpoint load; occupancy is rebuilt from entities. Persist targeting/stuck state that affects choices, but never serialize or hash distance grids or cache presence.

## Historical orders and identity

Each accepted command is an append-only event, identified independently of simulation ticks. Entity identity is a fixed-size causal tuple of scoped birth command, item index and loop occurrence. A command targeting multiple factories includes its frozen target index in the scoped birth command so their outputs remain distinct. Genesis uses a reserved namespace; blueprint sites retain their identity on completion. Delaying a birth does not change identity, and removing its cause leaves later references dormant. Revision-local compact indices optimize snapshots/events but are never order identities.

At each scheduled tick apply commands by accepted round, persisted player precedence rank, then command index. Explicit target IDs are sorted/frozen; group membership resolves from that tick's state. Rotate player precedence by round independently of arrival timing. Missing/dead/wrong-owner/incompatible targets become individual no-ops, never retargeted. Before an eligible action/setting applies, check its target's active order locks: a lock skips older-round events inside its following interval with `locked_by_later_round`. Same-round and newer-round events are unaffected. Group slot locks also guard group saved-order updates.

Before allocation, competing unstarted blueprints on one tile are ordered by their creation event's canonical precedence. Only the first eligible blueprint can request funding that tick; others demand zero. An unfunded winner reserves consideration only for that tick, not physical occupancy. Positive first funding creates the site and blocks the tile; no two sites can be funded onto the same tile.

New turns append commands that affect earlier simulation ticks; original archived inputs remain intact. AssignOrder/AssignGroupOrder may install following-interval order locks when they execute successfully. Keep installs none, DropWindow locks through t+W inclusively, and DropAll through the remaining match horizon. These are entity/group state, checkpointed and hashed; the controller does not precompute deleted-event sets. If a replacement's target disappears in the rewritten history, no lock is installed and its older future events can remain effective. Report that edge in command outcomes.

Locks retain enough independent round/expiry entries to preserve overlapping windows: a short newer lock cannot shorten a longer active one. Remove expired/dominated entries canonically. A blocked assignment installs no new locks. Future lookahead checks current lock state conservatively; unknown future group membership/births must not be incorrectly declared fully blocked. Replay and peripheral naturally derive locks from the selected revision's commands. Resimulate from the earliest new input tick as usual; checkpoint state restores all preceding lock effects.

Persistent control groups are part of the simulation rather than browser-only shortcuts. At command application, membership edits, factory bindings, group orders and individual orders follow canonical event order. Group commands resolve current living membership, save the latest order and write each compatible member’s action once; no per-tick group-order rebroadcast occurs. Each recipient applies through the same generic action assignment used by direct commands. Group slots and causal unit IDs remain stable when births move in time. UI previews of group membership are informative; actual replay membership can differ after earlier edits.

At successful factory output insertion, resolve the current output binding, register the newborn in that group, and assign its latest saved order and active group locks (or proposed factory-template fallback if no group order exists). Existing member-specific overrides are unaffected. Checkpoint suffix replay restores saved group orders and bindings before new births; a changed earlier group command invalidates all later derived birth orders in the suffix. Both worker and peripheral derive these assignments locally from the same ledger/state, rather than emitting synthetic player commands for newborns.

## Two-phase tick

1. Expire lock entries, apply allowed command assignments and queue edits in canonical order, and expire invalid targets deterministically.
2. **Action:** take a read-only view; compute legal attacks, mining, construction and production demands in parallel into slots indexed by sorted entity ID. Build spatial occupancy/buckets once. Target choice orders candidates by current support target, distance, then ID. Grid line-of-sight uses one specified integer traversal with symmetric endpoint handling and a fixture for corner cases.
3. Apply mining transfers in stable tile/entity order; allocate each player's bank through priority tiers using equal-share capped water filling. Roundoff is clamped at zero and accounted within a documented epsilon. Allocation and reductions run serially in stable ID order. One funded site is one consumer regardless of how many constructors contribute; its demand is their summed legal build rates.
4. Resolve damage/healing/construction HP growth simultaneously from the action snapshot. `hp' = min(new_max_hp, old_hp + funded_health_growth + healing - damage)`. Mark deaths after summation; units alive at phase start still contribute their action. Complete sites/production and reserve possible births in stable causal-ID order. No healing creates matter; healing, if enabled, must use finite matter or be explicitly free in content.
5. **Motion:** surviving pre-existing mobile entities compute destinations from the post-action occupancy. A unit that performed attack/mining/construction waits this tick; factories/static attackers never move. Blocked or ineligible action attempts do not consume the movement opportunity. Newborn units first act/move on the next tick. Resolve movement deterministically, then materialize eligible factory births on vacant outputs. A spawn cannot displace an occupant. Successful spawn, not funding completion, advances the queue occurrence and re-adds a looping item to the queue tail.
6. Advance cooldowns/tick, recompute both per-player survival predicates (including recovery), record transitions and evaluate inactivity cutoff with future-event/cooldown guards, record statistics/events, and hash canonical state as scheduled.

Cooldown semantics are absolute `next_action_tick` / `next_move_tick`, advanced only on executed action/move (blocked moves retry with a small fixed configured delay). Command changes do not reset cooldowns. This prevents rewrite spam from bypassing speed limits.

## Motion and AI shortcuts

Use shared destination flow fields: a BFS distance grid per `(goal_tile, neighbor_rule, structure_version)` over terrain and static structures/sites. Four-neighbor fields serve vehicles; eight-neighbor unit-cost fields serve walkers with no diagonal corner cutting. Fixed neighbor order breaks equal-distance ties. At each movement opportunity choose a legal neighbor with lower distance; dynamic occupants remain soft obstacles for the displacement phase. A 48×48 field has 2,304 cells, about 4.5 KiB with u16 distances; use an unreachable sentinel and validate map sizes or widen distances to avoid overflow.

Share fields across units for AttackMove, chosen mining/construction work tiles, follow targets and combat chase. A mobile enemy's tile can be a field goal because dynamic occupancy is excluded; stop at legal firing range rather than entering it. For static occupied targets use a virtual goal whose legal adjacent walkable cells seed the field, never a traversable structure tile. Support/work positions use the same deterministic nearest legal goal convention. No per-pursuer whole-map search. Short adjacent steps use the same neighbor/corner checks.

Unreachable is a field lookup result, not a fresh search per entity. Build needed fields once per key in canonical order before parallel readers use them, or use cache access that cannot alter decisions. Increment the local structure version and invalidate fields on blueprint placement, site creation, completion and structure/site destruction; dynamic movement does not invalidate fields. The entire bounded LRU and version are derived, omitted from checkpoint/hash and rebuilt after load. Eviction may cost time but cannot alter next-step decisions. This must hold for cold/warm caches and every worker count.

Treat dynamic occupants as soft obstacles for route selection, then resolve movement in one deterministic ordered pass. Allied bots may yield even when idle.

Proposed bounded displacement rule:

1. Sort eligible movement intents by deterministic rotating rank derived from seed/tick/entity ID, with ID as final tie-break. Maintain occupancy and a touched-entity set during the pass; an entity moves or is displaced at most once per tick.
2. An empty legal destination permits the move. An enemy, structure, construction site, or already-touched entity blocks it. Allied mobile occupants—including idle, working or cooling-down bots—may yield without having issued a reciprocal move.
3. For an allied blocker, inspect only its immediately adjacent tiles in a counter-based pseudorandom order keyed by seed/tick/mover/blocker. Prefer an empty legal neighbor other than the mover's source, then fall back to the mover's source as a two-unit swap if that step is legal for the blocker. Neighbor order does not use shared RNG or task scheduling. Both resulting moves must obey their own four/eight-neighbor terrain/corner rules; reject intersecting diagonal edges with already accepted moves.
4. Apply both moves atomically, mark both touched, update facing, retain orders/queue/group state and retain the shared field (dynamic occupancy does not change it). Forced displacement can occur while the blocker is on cooldown or has acted; this is an explicit traffic mechanic, not another attack/work opportunity. Set its next move opportunity to at least current tick plus its movement cooldown. Newborns remain ineligible until the next tick. No recursive push chains, teleportation, overlapping occupants or displacement of static buildings.
5. If no legal displacement exists, reject the intent and record a failed attempt. After three failed voluntary attempts at the same step, use a bounded local BFS of radius 6 with current blockers as hard obstacles, seeking a reachable cell of lower shared-field distance. Select by field distance, local path length and coordinates, then follow the bounded returned detour until reaching that lower-distance cell; serialize its remaining steps so a necessary uphill first step does not immediately reverse. Abort the detour on changed goal or an illegal next step. This is at most the local radius-6 search area, never a whole-map per-unit route. Reset on voluntary progress or changed goal/topology. If no route exists, wait for a relevant occupancy/topology change; retry scheduling itself is not progress or a reason to defeat inactivity stopping.

No placement rule can move a bot when every legal destination is rock/static/enemy-occupied; such units are visibly blocked. Crowded factory outputs can release already-spawned idle bots through ordinary allied traffic, but births themselves never displace occupants and a lone idle output still requires an order/group template to clear it, as requested.

Many-unit orders share one destination field; there is no per-unit destination spreading in the baseline. Once lower-distance exits are occupied by allies settled at the same goal, units wait rather than repeatedly displacing the settled cluster. Mark an entity settled only at distance zero or behind a lower-distance settled same-goal ally; the relation strictly descends field distance and cannot form a settlement cycle. Reevaluate when occupancy/order/topology changes. Ordinary transit blockers still yield through displacement. Preserve the goal and any settled/stuck state needed for identical checkpoint replay; only add individual destination assignments if automated crowd fixtures demonstrate a need.

Team membership defines hostility (proposed fixed alliances with no friendly fire). Ownership still governs orders and bank spending; allies may be followed/supported and participate in allied swaps. Player survival is evaluated individually, not through teammates’ capabilities.

## Combat behavior table

These are complete baseline proposals for generic weapon-capable entities, not additional user-locked mechanics. `engaged_target` in S[t] is last tick's committed combat target, not another worker's unfinished intent. Save it in checkpoints. At tick t read a single action snapshot; retain a valid target within this tick's acquisition zone, otherwise choose nearest legal enemy then entity ID. Require hostile ownership, living target, vision and line-of-sight for direct fire; indirect fire ignores intervening rock for shots but still uses configured vision/range. Clear a target immediately when dead, non-hostile or outside the relevant zone. No strategic AI opponent is required.

| Current order/capability | Acquisition and action | Motion / weapon cooldown |
| --- | --- | --- |
| Static weapon (turret) | Automatically acquire in the intersection of vision and weapon range, fire when ready | Never chase or move |
| Idle mobile with weapon | Defend against enemies already in legal weapon range | Hold position, including while cooling down |
| AttackMove before destination | Acquire within vision; pursue an acquired enemy until it leaves vision, otherwise proceed to assigned destination | Hold while target is in weapon range, even on cooldown; otherwise approach legal firing position |
| AttackMove at destination | Continue defending using in-range acquisition | Hold until order changes or destination becomes invalid; do not start a new chase |
| Mine / Construct | Perform the assigned economic work; this action mode does not automatically acquire combat targets | Approach legal work tiles; hold while working/cooling down |
| Support | Read the supported ally's `engaged_target` from S[t], assist if legal and within supporter vision; otherwise self-defend in range. A healing-capable supporter prioritizes legal healing of the supported ally over firing | Follow toward a free nearby tile, but do not chase an assisted enemy beyond the supported ally's vision-radius neighborhood; hold while firing/healing or in legal attack range on cooldown |

Unarmed units use movement/follow/economic behavior without attack intents. Support chains/cycles read prior committed targets once and never recurse. On each tick the selected target (or none) becomes the next `engaged_target`. A successful attack/heal/work consumes that tick's motion, as before; hold-on-cooldown is an additional explicit condition. Mining/building job selection uses stable distance/ID ties. A temporarily eliminated owner does not change any of these behaviors.

## Performance and data delivery

Use compact arrays and tile-indexed occupancy; avoid per-tick JSON and full-world clones. Parallel intent jobs read shared immutable phase data; one ordered reducer commits mutations. Worker stream batches are bounded; browser slowness cannot block simulation; required disk output may apply bounded backpressure as specified below. Send progress at most a few times per second. Measure wall simulation duration separately from simulated duration.

Initial measurement target, not a promise: default 48×48 map, 500 entities, 12,000 actively simulated ticks in under two seconds on the developer's recorded machine in release mode, peak server+worker memory under 512 MiB. Benchmark path-heavy and combat-heavy scenarios at 100/500/2,000 entities. If unmet, profile; first reduce snapshot frequency, unnecessary path work, and allocation. Do not weaken determinism to hit a benchmark.

Snapshot memory and browser delivery must be bounded: checkpoint interval configurable, compressed snapshot chunks on disk, bounded in-memory LRU, timeline overview fetched separately from selected-tick chunks. Browser requests revision-tagged tick ranges. Avoid broadcasting the entire history after each turn. Checkpoint pruning in timed mode retains `S[L]` and the replay archive needed for later audit.

## Peripheral mode

When configured for inputs-only delivery, main server still runs the authoritative simulation and owns scoring. A trusted native peripheral connects to its WebSocket, downloads pinned initial configuration/content plus the command ledger, and uses the exact same simulation library/build to reproduce revisions. It serves a local browser UI and local state snapshots; player commits relay to the main server using assigned slot credentials. Main server sends commands, phase metadata, scores/timing, and state hashes, not world snapshots in this mode.

Peripheral compares each completed revision's final hash and terminal tick with the controller's reference; mismatch stops local order entry (planning is not forwarded) and shows a diagnostic through the status endpoint and failed queries. It reconstructs from the initial state and ledger after reconnect or a runner restart, and regenerates evicted bodies by full replay with the hash re-checked; locally persisted checkpoints are not implemented (in-memory only). No automatic acceptance of client-computed wins, custom consensus, browser WASM port, or peer-to-peer synchronization. The ordinary authoritative mode remains the first playable milestone.

## Multiplayer result reduction

The worker returns all survivors and elimination reasons, not a single winner ID. Simulation continues regardless of the number of eligible players: continue to inactivity/horizon even when no player or only one side currently meets survival requirements. Persisting units keep orders, can cause subsequent mutual elimination, and can restore their owner by completing a factory. Do not use a monotonic ever-eliminated flag or disable AI by owner status. Classify the final survivor set as stalemate (everyone), win (some), or draw (none). The controller atomically applies all per-player/ per-team score deltas before checking a fixed target or lead over every rival, with configured tie policy. Stalemates never score; wins credit final survivors; draws use the none/all_players configuration. Checkpoints and replay outcomes preserve elimination and recovery timing; team assignments are pinned with match configuration. Constructor mining uses the ordinary mining action with half the dedicated miner rate, without an ID-specific engine branch.

## Minimal visual playback

The client renders user-requested grayscale terrain, high-contrast entities, health bars, facing, and lightweight movement/shot/impact effects. Movement resolution updates last-move direction only for successful moves, including allied swaps; attacks do not rotate this field. Emit compact canonical combat/movement events with frozen positions alongside snapshot chunks, retaining events that occur between samples. Cosmetic projectile travel does not change tick damage resolution. Effects are derived from selected replay time and revision, so seeking, pausing and suffix replacement do not replay stale explosions or change authoritative state.

## Player documentation build

The player guide is a static site generated once at server startup from the actual loaded/pinned content and served at `/guide/`. Proposed authored source is `client/guide/`; the coordinator-owned generator combines concise prose with tables from the same normalized content loader as the sim. Generate into a writable static directory; expose the URL only after successful generation. There is one generation path for ordinary launch, runtime YAML and resumed/replay content. The peripheral uses it with its own pinned content. No bundled-table comparison or build-time HTML path is required.

The site remains static between content loads; no hand-maintained stat numbers or separate documentation service. Historical replay guides can be generated on demand with the same function and content-keyed directory. Include content hash/rules build in metadata for traceability, not as an alternate generation path. Authored mechanics prose/hotkeys still require verification against behavior.

Tables show health, matter cost, weapon damage/range/vision, tick cooldowns, economic rates, movement neighbors and capabilities. Compute any per-second numbers from effective tick rate and include that rate in artifact identity. Do not invent final balance numbers before content exists. Startup rather than compile-time generation is an explicit assistant interpretation of the user's static-site preference, retaining one stat source and preventing drift.

## Lobby and stable server address

Lobby state is versioned independently from battlefield revisions. Accepted username, color, slot and team changes broadcast one complete roster to players and spectators. Start validates the displayed lobby revision, connected/claimed slots and configured team constraints, then freezes identity/team metadata for the match. Reject a stale Start request with the refreshed roster so a last-moment team/color edit is visible before starting. No extra ready-up ceremony is required by this proposal.

The server entry point parses a CLI port and binds that exact port for browser assets, guide, HTTP and WebSocket traffic. Proposed default 8080; fail instead of silently selecting another port. Relative client routes and a same-origin WebSocket keep the browser URL valid across restarts. Persist session slot tokens and roster metadata with the lobby/match; refreshing after resume restores identity and current phase. Bootstrap includes a server-instance identifier so stale jobs/responses from a previous process cannot be mistaken for the current instance. Explicit new-match startup may show a new lobby at the same address; do not promise the previous world survives without archive resume. Peripheral mode offers its own configurable local HTTP port and serves a guide matching its pinned content.

## Round latency, output pressure, and retention

Measure round performance beyond inner-loop throughput. Measure server receipt of the final commit → durable revision publication → browser exact-state-ready separately, including thread scheduling, checkpoint replay, event export, compression, fsync and client payload work. Record exact-tick cold/warm seek latency, peak server+worker/browser memory, bytes per revision and accumulated disk. Proposed provisional targets on a recorded developer machine: default typical round playable within 5 seconds, default cold seek within 250 ms; a full 20,000-tick default cap workload is reported separately and must not be represented by a 12,000-tick benchmark. Targets are profiling criteria, not promises or grounds to shrink requested scope.

Simulation-thread required batches use a bounded typed channel with an aggregate byte budget (proposed 16 MiB) drained into chunk files by the server; a slow disk throttles the producer rather than losing records or growing memory indefinitely. Optional progress updates may be coalesced. Disk-full/write failures stop publication, retain durable accepted inputs and report a retryable failure. Do not acknowledge a completed revision whose result records are missing. Bound batch and chunk sizes as well as channel byte usage; no simulation IPC framing is needed.

Keep pinned content/initial state, accepted turns/policies, per-round outcome/score/timing records and final hashes permanently for the match. Snapshot chunks, detailed per-tick stats/events and checkpoints are regenerable caches; evict by configured memory/disk budget while retaining logical round availability via regeneration from the archived ledger/build. Do not delete authoritative per-turn results to meet cache budgets. Track disk use and stop cleanly if authoritative storage cannot be written. Indefinite scoreboard rounds can grow archives; do not claim a fixed total disk bound.

## Inactivity reducer

Proposed progress is an executed voluntary movement step (including necessary detours), positive matter transfer/spend, effective nonzero damage/healing, completed construction/birth, or destruction. Mere targeting, group bookkeeping, cooldown countdown, failed movement, queue inspection and forced displacement alone do not reset activity. Voluntary pursuit/movement cycles can still hit the absolute cap, which is reported visibly.

After actions/motion update `last_progress_tick`, then test the configured quiet duration and minimum end. A future player command defers stopping unless current lock state proves every effect is blocked through that command tick. Treat unknown future births/membership conservatively as potentially effective. Legal future commands receive their opportunity to run. A cooldown defers stopping only if the action would be legal now if its cooldown were zero, with all other state frozen: target/range/LOS, resources, work tile and occupancy already satisfy execution. Unreachable path retries, unfunded demand, blocked outputs and destroyed targets fail this test. Free passage of time alone must enable the action; an anticipated external change is not sufficient. Fixed movement retry timers are never independent guards. Fast-forward only if every intervening phase is provably unchanged, advancing to the earliest legitimate cooldown/event/deadline and preserving ordinary-tick hashes and stop ticks.

## Ore and default horizon

Proposed default max_tick is 20,000. Size total accessible ore per starting allocation to approximately 10,000–20,000 ticks of one dedicated miner's continuous full throughput; use a lower initial target (about 12,000 mining ticks) so travel/quiet timeout fit beneath the cap in the ordinary mine-and-loop fixture. More miners deplete it sooner; constructor-only mining is half rate and may reach the cap. YAML can tune ore and horizon independently. Lobby shows `ore allocation / dedicated miner matter per tick` as an estimate assuming uninterrupted mining, alongside the hard cap; it is not a guaranteed battle duration. Typical peaceful loops should stop after ore exhaustion and inactivity rather than routinely hitting the cap. Measure both the ordinary opening and the full configured cap with exports enabled.
