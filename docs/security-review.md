# Network and host boundary review — 2026-11-10

Scope: remotely reachable HTTP/WebSocket input that could execute code, select a process to run, or read/write outside game storage. Cheating, account impersonation and a compromised GitHub repository are outside this review's requested focus. This is a source review with targeted regressions, not a penetration-test certification or dependency/CVE audit.

## Fixed: public simulation thread amplification

`POST /api/games` accepted any positive `u16` simulation-thread count. Once the simulation has enough armed entities to use parallel intent processing, `crates/sim/src/tick.rs` splits entities into that many chunks and spawns an OS thread per chunk. A high submitted value could turn an ordinary large army into hundreds or thousands of thread creations per tick. This is resource exhaustion, not arbitrary code execution.

Public game creation now rejects a thread count above the coordinator's trusted startup configuration. Worker launch also refuses persisted games above that budget, so older directory records cannot bypass the check on restart. The default budget is four threads per game; operators can change their local config. Standalone local simulation remains unchanged. Lowering the host budget below an existing game's configuration makes that game unavailable until the operator restores an adequate budget; the server does not silently rewrite pinned replay settings.

## Reviewed boundaries

- **Processes:** coordinator workers use `std::process::Command` with the current executable and separate arguments. HTTP names, passwords, feedback and gameplay commands are not shell commands or executable paths. Workers bind loopback; only the coordinator forwards public game WebSockets.
- **Storage:** public game IDs are generated by the server. Game access resolves IDs through the directory; replay and feedback IDs use an alphanumeric/hyphen allowlist. Public creation pins `replay_directory`, and worker replay paths are selected by the coordinator. Numeric round/player/revision identifiers determine archive filenames; request IDs are saved as data, not interpolated into filenames.
- **Static files:** client and guide reads are rooted in operator-selected asset directories and reject empty, absolute slash-prefixed and parent-traversal segments. Those directories are trusted local deployment assets: symlinks placed there by an operator can expose their targets. No network endpoint creates symlinks or uploads files into those roots. Do not point the asset root at the repository, home or state directory.
- **Parsing and rendering:** network commands deserialize into typed Rust enums/structs; the reviewed application paths do not use a scripting evaluator, dynamic library loader or unsafe application code. Lobby names and feedback render through text nodes, not user-authored HTML. Guide prose and SVG templates are repository-authored trusted assets.
- **Updater:** `scripts/host.py` executes argument lists, fetches `origin/main`, and intentionally runs repository builds from that revision. Repository/dependency/build-system compromise can execute code as the service account; that is part of the accepted trusted update boundary, not an HTTP update hook. Network game actions cannot name an update revision or create the supervisor's update-request file.

No direct unauthenticated remote-code-execution or arbitrary outside-root write path was found in this pass. That is a bounded finding about the reviewed application code, not a guarantee about every dependency or deployment.

## Verification and remaining limits

Targeted tests reject an oversized public thread request before any directory entry or worker is created, refuse an oversized persisted game at worker launch, and check that static-file reads cannot escape their root using parent/absolute path forms. Existing replay-identifier tests cover path separators and encoded identifier forms. All 31 server tests and server Clippy with warnings denied passed on pinned Rust 1.97.1; formatting and diff checks passed. These are direct handler/file-boundary tests, not a live Internet exploit test. No UI changed, and the full workspace/browser suites were not rerun for this server-only patch.

The server still has no overall worker, connection, request-rate or disk quota. Strangers can consume resources by creating many otherwise valid games, holding sockets or requesting expensive replay data. Casual passwords and identity cookies are not strong authentication. Those are separate availability/access-control concerns; this change deliberately does not introduce an account system or a broad public-service hardening architecture.
