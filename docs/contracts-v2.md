# Contract version 2 (stabilized at Gate 2)

The [Rust records](../crates/contracts/src/types.rs) and [generated JSON Schema](../schemas/contracts-v2.json) are the shared foundation for the [current architecture](contracts.md). They now describe a working slice: the engine, server and browser exchange exactly these records. Breadth agents build against them; compatible additions go through the coordinator and regenerate `schemas/`, `client/src/contracts.generated.ts` and `fixtures/` in the same change. Version 2 rejects version 1 records; no archive migration is provided.

Tagged unions use `kind` with snake_case names. Network envelopes carry numeric `schema_version: 2`; server replies also carry `server_instance_id`, and a client treats a changed instance as a new server (refresh). Unknown versions/fields are rejected. Optional fields serialize as null. Wire integers use bounded u8/u16/u32 or `SafeInt`. Group slots are 0–9. Ranges are inclusive unless explicitly exclusive. S[t] is before tick t; executing t produces S[t+1]. Schema validation does not replace exact-state ownership/capability/phase validation, which the server performs on commit.

## Identities, checkpoints and locks

CommandId is `{round, player, index}`; BirthCommandId adds `target_index`; EntityId adds `item_index` and `occurrence`; QueueItemId omits occurrence. Genesis reserves round zero. Blueprint sites keep their identity on completion. Loop occurrence advances only at successful output insertion (implemented in `crates/sim/src/tick.rs::births`). `draft::resolve_local_references` resolves sequential backward references at commit.

Canonical world JSON sorts keyed sets and validates finite resources/health, grids, occupancy and transition history; SHA-256 of it is the state hash. Cooldowns, facing, targeting, birth timing, `goal_settled`, bounded `local_detour`, entity/group locks and survival transitions affect hashes. Flow-field grids, cache presence and structure versions are absent; checkpoint reruns hash-match full replays in the engine tests.

`locks::{blocks,install,canonicalize}` implement following intervals; the engine installs locks only after a successful assignment, checks member and slot locks separately, and births inherit active group locks. `CommandOutcome` reports `locked_by_later_round`, `absent`, `wrong_owner`, `incompatible`, `blocked` and `missing_support_target` per target.

## Simulation boundary

`SimRequest` is an owned job: checkpoint, the full ledger of accepted turns, per-round precedence, `end_tick_exclusive`, `minimum_end_tick` and the parent revision's `entity_dictionary`. The server thread returns `WorkerMessage::Batch { dictionary, samples, checkpoints, stats, events, timeline }`, `Progress`, then `Complete { outcome, final_hash, sim_duration_ms, command_outcomes }` or `Failed`. A job runs from the latest checkpoint at or before the earliest new input tick; the server reuses the parent's data before that tick.

Compact transport: `EntityRef { id, owner, type_key }` entries are appended to a per-revision dictionary in birth order and never reused; `Sample { tick, players, entities: [{index, tile, hp, facing, lifecycle, activity, engaged}], ore: [{index, remaining}] }` references entities by dictionary index. `index_width` reports 16 or 32 from the dictionary size; JSON carries plain integers either way. Durable orders, hashes and events use causal tuples. `TimelineBucket`s are emitted per snapshot interval per player per activity; the server publishes a coarser index (20 ticks, dominant activity by combat > construction > mining > movement > idle) in `RevisionPublished`.

Presentation events are `attack`, `impact`, `destroyed`, `displacement` and `survival` with frozen tiles and per-job sequence numbers. `move` remains defined but is not emitted: samples every 5 ticks carry positions, and per-step move events would dominate volume (see [measurements](gate2-measurements.md)).

## Browser protocol

`hello{slot_token?}` → `welcome`, then, once a match exists, `revision_published` for the current revision and `planning_opened` when planning is open; a repeated hello on the same socket is idempotent. `claim_slot` → private `slot_claimed`; every lobby change broadcasts `lobby_updated`; `start_match` is validated against the displayed lobby revision and rejected with the refreshed roster when stale. `planning_ready` starts a player's thinking timer. `commit` returns `commit_accepted` (idempotent by `request_id`) or `commit_rejected`; each accepted commit re-broadcasts `planning_opened` with the updated `committed_players`. When all players committed, `simulation_progress` messages precede `revision_published` and the next `planning_opened`; `match_finished` closes a scoreboard/timed match.

Range queries: `get_snapshot_range` → `snapshot_range` (dictionary plus samples at the requested stride), `get_events` → `events`, `get_stats` → `stats_range`, `get_commands` → `commands`, `get_exact_state` → `exact_state` (reconstructed in-process from the nearest checkpoint, cached in a small LRU, never snapped), `get_control_groups` → `control_groups`, `get_round{revision}` → `round_result` (round/parent, published outcome/timeline/score/timed result, committed thinking totals, simulation duration and authoritative command outcomes). Historical metadata is read-only and uses that revision’s accepted ledger, including diagnostics retained before its reconstruction checkpoint. Responses are matched by revision and tick; the client ignores stale revisions. `stop_and_archive` records an unfinished archive.

## Inputs-only peripheral protocol

A peripheral connects to `/ws/peripheral` and sends `hello` without a slot token. After `welcome`, and again whenever a revision is published, it receives what it still lacks in order: `replay_bootstrap{fingerprint, config, content, initial_state, ledger, precedence}` once a match has started (ledger/precedence are the current revision's), then for every published revision `round_inputs{revision, turns, precedence, editable_from}` (that round's accepted turns and precedence; `editable_from` is the lock boundary the controller's job ran under, the parent's timed boundary or 0, which fixes `minimum_end_tick`) followed by `reference_hash{revision, tick, hash}` (terminal state tick and final state hash), then the ordinary `revision_published`/`planning_opened` broadcasts. World-state queries are refused on that route, and on `/ws` too when the server runs with `--inputs-only`; `get_commands` and `get_round` stay available. Player tabs behind a peripheral use `/ws` through a relay with their own slot tokens, so lobby, readiness, commit and stop semantics are unchanged.

## Content, guide and configuration

Content loading/normalization is shared; the sim reads capability data only. The server generates the guide once at startup with `write_guide` from the effective content and serves it at `/guide/`; `/guide/content.json` is the client's type table. `config/game.yaml` pins seed, map, players, objective, control limit, future-order window, horizon/stall, the decided stop, snapshot/checkpoint intervals, starting matter and ore per start; the map generator supports connected two-to-four-player cave maps, with symmetric two/four-player layouts and asymmetric three-player layouts.

## Still provisional

Compact binary encodings (JSON only today) and `Move` events. The inputs-only transport is implemented as described above; a dedicated peripheral status message is not part of the records (the runner reports over HTTP at `/peripheral/status`). Retention budgets, archive resume, lobby team capacity and server-side stats bucketing are implemented in the server without record changes: `get_stats` buckets report the latest `StatsSample` in each bucket, and timeline index buckets widen with the run length. Changing any record is a coordinator change with regenerated schema/types/fixtures.

## Blueprint planning and factory order delivery

`ConfigureBlueprints { blueprint_ids, settings }` uses the existing sequential draft/persistent blueprint reference format. Settings replace the planned queue, priority, loop flag and newborn order. Only owned, unfunded blueprints accept it; once a site exists, normal entity production/settings commands apply. Queue identities are derived from the configuring command plus the sorted/deduplicated target index and recipe index, separate from the placement identity. Settings and their birth-command source persist in checkpoints; absent optional fields are omitted so older unconfigured blueprint serialization/hashes remain stable. Construction consumes these settings when creating the site and preserves them through completion. Configuration requires `keep` and counts as a command under the control limit.

Normal direct/group action delivery to a factory sets its newborn template, installs the same action replacement locks, and records the factory among applied recipients. It leaves production running; later newborns read the effective output-group order or fallback template. Existing `SetStoredOrder` records remain replayable. Sites with production accept this configuration before completion.

`get_events.effects_only` is an optional boolean (omitted/false preserves complete diagnostics). The browser sets it to receive attack, impact and destruction effects, since snapshot interpolation already renders movement. Filtering preserves authoritative event ticks and sequence numbers.
