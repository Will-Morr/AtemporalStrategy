I have a weird idea for a video game that I want to make. I want to make a turn-based RTS that allows time travel. The core game is your standard RTS game where two players are giving commands to units that can collect resources, produce new units and attack each other. A normal RTS game can be mentally framed as a core simulation and a set of space-time inputs. I want to build an RTS where you are allowed to scrub backwards and forwards through time. As a first pass, let's do a turn-based RTS where the game simulation runs all the way through every tick. Both players have a chance to look through the timeline and to choose a place to inject orders. Once they have chosen their timestamp they can add however many orders they want to at that timestamp. This functionally allows them to change the objective of every unit and building, so they can queue up new units to be built or set new unit Target positions. I am expecting a minimal grid-based 2D system, buildings and units both take up one tile and units. Move horizontally or diagonally. For the first pass, let's do a simple game themed around fighting robots swarms. There should be two types of orders, general and unit specific. General orders are primarily things like building buildings, where a number of buildings can be put on the queue to be constructed. Unit orders are applied to individual units. The most common unit order is the standard RTS attack move, where units move to a Target position and attack any units that come within line of sight that they see. Support is an action where units follow closely behind a Target, attacking anything that it attacks or healing it or otherwise supporting it as it takes damage. Construct or mine should also be unit orders, where a square area is input and the units either construct queued buildings within that area, move to ore locations and collect resources. Constructing units should be done via a queue, with an option to loop the queue so build orders are re-added to the end of the queue when executed. Factories should have an option for a stored order, where new units are issued an order immediately after being built. This should be functionally required, as otherwise units stand on the output and block new unit construction until they are moved. 

The game should have a simple single resource system called matter. Matter should be mined and spent continuously. Units that are mining on an ore tile should be subtracting a fixed amount from that tile every tick and adding it to the player's sum. Ore tiles have a fixed, large sum of matter available that decreases when mined. Units or buildings that spend matter also do it continuously. Things under construction are tracked as a fraction of completeness set by the matter spent and the matter cost. The health of a partially complete building is set by this fraction. One of the configurations for units or buildings should be resource priority. This should be high medium or low. If more matter is being spent then mined, it should be spent evenly across all consumers according to tier, where higher tiers get absolute priority. If high tier consumers use all of the demand, then medium and low tiers should not advance at all and so on. 

From a generalized control perspective, units should have a set of controllable values that primarily exist as their current action, their resource priority, and their build queue if they are a factory. Things like unit stats and controls should all be implemented in a generalized way, rather than hard coded checks for specific unit IDs in code. These should all set as flags by-unit type. 

To start out with, let's have a very simple unit roster with constructors, miners, tanks, artillery, scouts, grunts, and grinders. Constructors and miners should do what they suggest. Tanks are expensive, high high health, and decent damage. Artillery is weak but long range. Scouts are fast with good vision but weak. Grunts are the generic cheap mass unit. Grinders are high damage melee units. For buildings, let's have factories that build units, turrets that provide long-range static defense, and walls have a decent amount of health but nothing else. Units should be split into walkers and vehicles, with walkers able to take diagonals and vehicles only moving on axis. Make sure the path planning is handled correctly for all of these. 

Implement simple map generation, where both players start with a single miner and constructor in opposite corners of a square map. Map generation should be done so that the two halves of the map are rotarily symmetric so neither player has an advantage. Map construction should be done as a series of connected rooms in the rough walled style of caves. 

Units should be implemented in a generic way, where units are built out from configuration files and assets and any unique abilities are described as tags. Start with extremely simple art, just using basic circles and rectangles to have some level of visual discrimination for what each unit is. The units should be colored according to the player color. The single most challenging part of this implementation is the need for extremely fast sim performance. While the Sim runs, both players will largely just be sitting there waiting. It would be nice to live stream the sim status as it runs to both players but is not strictly required. Implement the core game simulation in rust and multi-thread for performance where possible. For the actual game client, I am hoping to have this be entirely in browser to simplify sharing. Only implement the core game for now, where players open the port that the server is on and either claim a slot as a player before the game is started or just spectate the game. You do not need to worry about cheating, this is only a prototype do not overthink what information is sent to the clients. 

I am expecting to have most of the screen taken up by the actual map, where players can zoom in and out, drag the viewing window, move the camera with wasd, select individual units or groups of units using the standard left click select with shift to add to selection. It should be easy and seamless to give orders to multiple units and give large numbers of orders. I am expecting the standard minimap in the bottom right corner and selection information in the bottom left. The center should be taken up by the timeline. The timeline should have options to play back gameplay at a selected rate, as well as jumping forwards and backwards by small and long amounts. The review system should jump to where you click, as well as being zoomable and draggable like a standard video editing timeline. It should also have a basic color code to indicate what the most significant event occurring at that time is for your army, like combat, construction, moving, or idling. The scale of the event should be communicated with a vertical bar, so the timeline kind of looks like a long-running multicolored bar plot. Make sure to include hotkeys for all actions. The game should be entirely playable where the mouse only selects units and tiles on the map while keys are pressed to select what actions are being taken. 

Include some basic options for game setup, where the default is 1v1 on a symmetric map but map symmetry can be disabled and larger player counts is supported. Game setup should just be a yaml file, changing the game configuration should be simply modifying this file and restarting the server. This is a hacky prototype, not a production game. An additional configuration should be game objective. How to determine who is winning is the weirdest part of the style of game. Let's start with two basic options. Timed mode is a game mode where every tick the start time of the simulation advances forward by some amount. This should lock the first n number of ticks of the game forever. This means that eventually the game has to end as there's some amount of immutable game history. The second mode should be scoreboard. A player scores a point when their army has won at the end a simulation run after a turn. Let's define winning as having destroyed all enemy factories for both game modes. An additional configuration should be control limits. By default, every turn, a player selects a tick to control. The player can then send as many new orders as they want to their machines. An interesting alternate mode would be single order. This means that a turn is giving a single order to a unit or group of units on a specified tick. This means that queuing the construction of a building or a line of buildings takes a whole turn. This also limits the way players could move units, where redirecting all units to a new target location takes a whole tick. Make sure that action selection is always undoable, where players can keep tweaking the input they want to give until they hit a large button indicating that their move is done. Log the amount of time each player took per turn, as well as SIM time. Include a game configuration that penalizes players for taking more time in the score based mode based on the ratio in total turn time between the two players. This ratio should be displayed regardless of whether or not the game mode is enabled. 

For actual core game architecture, I expect the default to be a core server process that handles IO and manages the game data and spins up a simulation process when actually trying to execute ticks. The simulation should only be executed starting at the earliest time a player changed the timeline. There should be an optional server configuration to share player inputs and not actual game information. This requires a second game process mode that acts in a controller peripheral style, where the main server is still handling the move ticks, handling player inputs, and tracking score. The independent process is then able to receive these instructions and execute a SIM in parallel that reaches the same conclusions as the main sim. This means that determinism is a core aspect of the simulation and cannot be broken. All multithreading should be done in a guaranteed repeatable way. I'm expecting multi-threading to primarily be used to accelerate calculation of unit AI and for the actual core SIM loop to generally be a high-speed single thread. Generally speaking, stats such as unit health and damage should all be handled in floating point space, so unit health at the end of the tick is a simply previous health minus damage plus healing so math could be done in parallel. Every tick should be split into two phases, action and motion. All units that are taking an action, such as construction or attacking, should be able to be handled in parallel in one go. Motion is slightly trickier, as units cannot occupy the same tile and thus may need to collide. This should still be done as lightweight as possible. I suspect the best way to run the core simulation is multi-tick cooldowns, where units have a number of ticks required between moves and between actions that do not need to be the same number but mean that generally speaking most units don't move on most ticks. This should help keep things simple, as multiple units trying to move on to the same tile can just be ignored or handled pseudo-randomly and the other unit can move on its next tick. Try to keep unit pathfinding as simple as possible to be lightweight. It is totally acceptable to add mechanics purely to make paths simpler. An obvious version of this would be to have allied units trying to path through each other just having the two units swap tiles rather than constantly repathing around each other which becomes very expensive. I am open to proposals for other hacks to keep the sim lightweight. 

The one last feature request I have is game replays. Every turn should be saved as a file storing all player inputs by turn, as well as the result of each turn. This should basically for free give us the ability to resume games in case of crash or needing to pause.

The core objective of this iteration is seeing whether or not this game can be fun, not making sure it's the most beautiful, balanced game of all time. Stay focused for this initial implementation on simulation speed, sim stability, and user experience. Keep the game otherwise mechanically and visually minimal. I expect there to be a bunch of trade-offs with focusing on Sim speed. Things like recompiling the game in order to change unit stats or map parameters is totally fine. Start by building out a plan for the game entirely in markdown files in this repo. Ask for user input when a major decision has been under specified by the doc. The objective of the architecture pass is for all major decisions to be nailed down, and for sub agents to be able to independently implement subsystems. This means we should also most likely have data contracts laid out for the sub-agents to work with. Be intentional and prepared for adversarial review. If any major decision made here is flawed, push back but make sure to get review on changes. This entire system is expected to be One big short-lived experiment, and is most likely getting trashed after play testing. Keep this in mind while making decisions. We do not need an infinitely scalable maintainable system, we need an MVP that is pleasant to play.
